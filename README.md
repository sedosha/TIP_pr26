# Практическое занятие №10. Горизонтальное масштабирование: использование Load Balancer (NGINX)

# Цель занятия
Освоить базовый подход к горизонтальному масштабированию backend-приложения за счёт запуска нескольких экземпляров одного сервиса и распределения входящих HTTP-запросов через NGINX в роли балансировщика нагрузки.

## Архитектура решения

- **Backend-сервис** – HTTP-сервер на Go (tasks), реализующий эндпоинты:
  - `GET /health` – проверка состояния, возвращает JSON с полем `instance` и заголовок `X-Instance-ID`
  - `GET /v1/tasks` – возвращает список задач (статический), также добавляет заголовок `X-Instance-ID`
- **Балансировщик** – NGINX, настроенный через `upstream` на три реплики backend-сервиса.
- **Среда запуска** – Docker Compose:
  - три контейнера `tasks_1`, `tasks_2`, `tasks_3`
  - один контейнер `nginx_lb`, пробрасывающий порт 8080 наружу
- **Дополнительное задание** – добавлена третья реплика (`tasks_3`), все три участвуют в балансировке.

## Конфигурация NGINX (upstream с тремя репликами)

```nginx
events {}

http {
    upstream tasks_backend {
        server tasks_1:8082;
        server tasks_2:8082;
        server tasks_3:8082;
    }

    server {
        listen 8080;
        location / {
            proxy_pass http://tasks_backend;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Request-ID $request_id;
            proxy_set_header Authorization $http_authorization;
        }
    }
}
```

## Docker Compose (три реплики)

```yaml
version: "3.9"

services:
  tasks_1:
    build: ../../services/tasks
    container_name: tasks_1
    environment:
      APP_PORT: "8082"
      INSTANCE_ID: "tasks-1"

  tasks_2:
    build: ../../services/tasks
    container_name: tasks_2
    environment:
      APP_PORT: "8082"
      INSTANCE_ID: "tasks-2"

  tasks_3:
    build: ../../services/tasks
    container_name: tasks_3
    environment:
      APP_PORT: "8082"
      INSTANCE_ID: "tasks-3"

  nginx:
    image: nginx:1.27-alpine
    container_name: nginx_lb
    ports:
      - "8080:8080"
    volumes:
      - ./nginx.conf:/etc/nginx/nginx.conf:ro
    depends_on:
      - tasks_1
      - tasks_2
      - tasks_3
```

## Контрольные вопросы
1. **Что такое горизонтальное масштабирование?** Горизонтальное масштабирование — это увеличение пропускной способности системы не за счёт усиления одного узла, а за счёт добавления нескольких экземпляров одного и того же сервиса, работающих параллельно. Например, вместо одного мощного сервера запускаются три одинаковых контейнера tasks_1, tasks_2, tasks_3, а балансировщик распределяет между ними запросы. Такой подход позволяет наращивать мощность практически без ограничений и повышает отказоустойчивость.

2. **Чем оно отличается от вертикального масштабирования?** Вертикальное масштабирование означает увеличение ресурсов одного экземпляра (больше CPU, оперативной памяти, дискового пространства), что рано или поздно упирается в физические пределы машины. Горизонтальное масштабирование добавляет новые экземпляры, что теоретически бесконечно, но требует дополнительной инфраструктуры (балансировщика, общего хранилища состояния). Вертикальное масштабирование проще в реализации, но горизонтальное лучше подходит для высоконагруженных распределённых систем.

3. **Зачем нужен load balancer?** Балансировщик нагрузки принимает входящие запросы от клиентов и распределяет их между несколькими доступными экземплярами бэкенд-сервиса, скрывая внутреннюю структуру. Он предотвращает перегрузку одного экземпляра, обеспечивает отказоустойчивость (при падении одного узла трафик перенаправляется на живые) и даёт единую точку входа для клиентов. Без него клиентам пришлось бы самим решать, какой адрес реплики использовать.

4. **Какую роль в этой работе выполняет NGINX?** NGINX выступает в роли обратного прокси и балансировщика нагрузки: он слушает внешний порт 8080, принимает все клиентские запросы и проксирует их в upstream-группу, состоящую из трёх реплик tasks (tasks_1, tasks_2, tasks_3). NGINX автоматически распределяет запросы между репликами, прокидывает необходимые заголовки и, при недоступности одной из реплик, перестаёт направлять на неё трафик, обеспечивая отказоустойчивость.

5. **Что такое upstream в NGINX?** Upstream — это блок конфигурации NGINX, который описывает группу бэкенд-серверов, между которыми будет распределяться нагрузка. Внутри блока перечисляются адреса и порты серверов (например, `server tasks_1:8082;`), и NGINX по умолчанию использует алгоритм round‑robin для последовательного направления запросов к каждому из них. Upstream позволяет абстрагировать бэкенды и легко добавлять или удалять реплики без изменения основной логики проксирования.

6. **Почему для горизонтального масштабирования желательно делать сервис stateless?** Stateless-сервис не хранит важное пользовательское состояние в своей локальной памяти (зависит только от внешних хранилищ, например БД или Redis). Если сервис хранит состояние внутри процесса, то при переключении запроса с одной реплики на другую данные могут быть потеряны или клиент получит противоречивые результаты. Stateless-архитектура позволяет произвольно добавлять, удалять и балансировать реплики без риска рассинхронизации данных.

7. **Зачем нужен health endpoint?** Health endpoint (например, `GET /health`) предоставляет простой способ проверить, что экземпляр сервиса жив, готов принимать запросы и не находится в состоянии сбоя. Балансировщики нагрузки (в том числе NGINX) могут периодически опрашивать этот эндпоинт, и если он перестаёт отвечать 200 OK, то реплика исключается из upstream-группы. Для разработчика это также удобный инструмент для ручной диагностики.

8. **Почему полезно добавлять X-Instance-ID?** Заголовок `X-Instance-ID` позволяет клиенту или администратору однозначно определить, какой именно экземпляр сервиса обработал запрос. Это даёт наглядное подтверждение работы балансировщика: выполнив несколько запросов, можно увидеть, что ответы чередуются между разными репликами. Также такой заголовок упрощает отладку — по нему можно отследить, на какой узел попал проблемный запрос.

9. **Что происходит при остановке одной из реплик?** При остановке одной реплики (например, `docker compose stop tasks_1`) NGINX продолжает отправлять запросы на оставшиеся работающие экземпляры. Поскольку недоступный сервер не отвечает, NGINX автоматически исключает его из ротации (в зависимости от настроек таймаутов и `max_fails`). Клиент при этом не замечает проблемы — он получает ответы от других реплик, а общая работоспособность системы сохраняется.

10. **Почему клиенту удобнее работать с одной точкой входа, а не с несколькими адресами реплик?** Единая точка входа (например, `http://localhost:8080`) скрывает внутреннюю архитектуру и избавляет клиента от необходимости знать все адреса реплик, управлять их списком или реализовывать собственную логику распределения запросов. Клиенту достаточно знать один стабильный адрес, а балансировщик сам решает, какую реплику задействовать. Это упрощает интеграцию, настройку файерволов и делает систему более гибкой при масштабировании.
